# WordPress 插件审核与开发自查指南

这份指南整理自 A Ripple Song 的两封 WordPress.org 插件审核邮件，以及修复过程中的补充验证，供后续开发插件时复用。

它覆盖本次遇到的问题，不代表 WordPress.org 的全部审核规则，也不保证照单完成就一定获批。提交时应同时阅读最新官方指南，并以审核团队对具体插件的意见为准。

## 1. 本次审核涉及哪些问题

| 项目 | 来源 | 开发时的要求 |
| --- | --- | --- |
| 动态输出未恰当转义，或转义时间过早 | 两封审核邮件均明确指出 | 按最终输出上下文转义；检查全部同类输出，而不只修改邮件列出的示例 |
| 全局名称前缀过短、容易冲突 | 人工审核邮件明确指出 | 使用足够长且独特的前缀或命名空间；同时检查 PHP 和 JavaScript 全局名称 |
| 未经明确同意加载外部 Google Fonts | 自动预审邮件明确指出 | 审查第三方请求和数据传输；优先移除不必要的外部资源，不能只补一段隐私说明 |
| 修复后的功能测试和提交流程 | 审核邮件明确要求 | 在干净 WordPress 环境开启调试测试，上传修正版，再回复原邮件线程 |
| RSS XML 转义、SVG 和音频白名单等细节 | 本次补充检查发现 | 作为输出转义专项检查；这些不是审核邮件逐项列出的原文要求 |
| 翻译加载建议、开发文件打包提示 | 本地 Plugin Check 发现 | 结合插件用途和实际发布包判断，不能把每条 warning 都当成相同级别的错误 |

## 2. 动态输出：按上下文、尽量晚转义

### 2.1 区分验证、清洗和转义

- **验证（validate）**：检查输入是否符合预期，例如枚举值、权限、数值范围。
- **清洗（sanitize）**：把输入整理成适合存储和处理的形式。
- **转义（escape）**：在输出时防止数据突破当前 HTML、属性、XML 等上下文。

保存时做过清洗、数据来自数据库、字符串由插件自己生成，都不能自动替代最终输出时的转义。翻译文本和 nonce 输出到 HTML 时也要按上下文处理。

不推荐把“以前已经转义过”作为默认输出约定：

```php
$title = esc_html( get_option( 'a_ripple_song_title' ) );
// 中间还可能修改 $title。
echo $title;
```

更容易维护和审核的写法：

```php
$title = get_option( 'a_ripple_song_title' );
echo esc_html( $title );
```

### 2.2 输出上下文速查

| 输出位置 | 常用处理 | 注意点 |
| --- | --- | --- |
| HTML 标签中的纯文本 | `esc_html()` | 不适合需要保留的 HTML 片段 |
| 普通 HTML 属性 | `esc_attr()` | 属性值加引号；拼接完成后转义整个值 |
| HTML 中的 `href`、`src` 等 URL | `esc_url()` | 不要用 `esc_attr()` 替代 URL 协议处理 |
| `<textarea>` 内容 | `esc_textarea()` | 不能直接输出保存的正文 |
| 允许文章级 HTML 的片段 | `wp_kses_post()` | 不是支持任意 HTML、SVG 或媒体标签的万能函数 |
| 需要精确控制的 HTML/SVG | `wp_kses()` 加专用白名单 | 同时限定标签和属性，测试功能是否保留 |
| XML/RSS 普通文本及属性 | `esc_xml()` | 不要默认沿用 HTML 模板的转义函数；CDATA 另行处理 |
| XML 中的 URL | URL 清洗后按 XML 上下文转义 | 例如 `esc_xml( esc_url_raw( $url ) )` |
| HTML 属性中的 JSON | `esc_attr( wp_json_encode( $data ) )` | JSON 编码之后仍需处理外层 HTML 属性 |
| 数字 | 输出时显式转换，或按需要格式化 | 例如 `(int) $post_id`、`absint( $count )` |

`esc_url_raw()` 适合存储或取得未做显示实体编码的 URL，**不能单独作为 HTML 输出转义函数**。

```php
<a href="<?php echo esc_url( $url ); ?>"
   class="<?php echo esc_attr( $prefix . '-button ' . $extra_class ); ?>">
    <?php echo esc_html( $label ); ?>
</a>

<textarea><?php echo esc_textarea( $value ); ?></textarea>

<div data-config="<?php echo esc_attr( wp_json_encode( $config ) ); ?>"></div>
```

翻译文本也使用匹配上下文的函数：

```php
esc_html_e( 'Save settings', 'a-ripple-song' );
echo esc_attr__( 'Player settings', 'a-ripple-song' );
```

### 2.3 不要把整段属性字符串直接 echo

本次审核明确指出了这一类代码：

```php
<input<?php echo $control->attributes(); ?>>
<span<?php echo $plays_attributes; ?>></span>
```

即使属性构建器内部做过转义，最终输出位置仍不容易确认它是否安全，人工审核也可能要求改为更明确的晚转义。

优先在模板逐项输出，或者让渲染函数在真正输出每个属性时转义：

```php
<input
    type="text"
    name="<?php echo esc_attr( $name ); ?>"
    value="<?php echo esc_attr( $value ); ?>"
>
```

属性渲染器需要明确区分普通值和 URL，并正确处理布尔属性。属性名应来自固定、受控的定义；`esc_attr()` 本身不负责把任意字符串验证为合法属性名，也不负责禁止事件属性。

### 2.4 `phpcs:ignore` 不能代替修复

这类注释只会影响静态分析工具：

```php
// phpcs:ignore WordPress.Security.EscapeOutput.OutputNotEscaped
```

它不会增加运行时安全性，也不会自动让人工审核接受输出。

使用忽略注释前，先确认是否能在输出处直接调用合适的转义函数。确实需要自定义上下文处理时，应说明准确的安全边界，尽量缩小忽略范围，并保留行为验证。例如 CDATA 边界处理有其特殊性，不能为了让工具安静就把整个模板的检查关掉。

### 2.5 SVG 图标：用专用白名单

内置文件、固定图标名，以及对文件名使用 `sanitize_file_name()`，都不能等同于对最终 SVG 标记做过滤。

最终输出可以采用：

```php
echo wp_kses( $svg, $allowed_svg );
```

白名单应覆盖实际使用的绘图标签和必要属性，例如：

- `svg`：`xmlns`、`viewbox`、尺寸、描边、`class`、必要的 ARIA 属性。
- `path`：`d`。
- `circle`：`cx`、`cy`、`r`。
- `rect`：位置、尺寸、圆角属性。

不要为了兼容而直接放开 `script`、`foreignObject` 或 `onload`、`onclick` 等事件属性。需要链接、渐变、外部引用等复杂 SVG 功能时，应单独审查。

也不要直接使用 `esc_html()` 或 `wp_kses_post()` 处理整段 SVG：前者会把图标显示成文字，后者通常会删除 SVG 标签。

验证时应同时检查恶意标记能否被过滤，以及图标的实际绘制效果。KSES 可能把属性名转为小写；浏览器按 HTML 解析 SVG 时会调整 `viewbox`，不能只凭字符串大小写不同判断图标已经损坏。

### 2.6 音频 HTML：保留必要的 `<source>`

`wp_audio_shortcode()` 的默认路径会处理许多属性，但它的返回 HTML 还可能受到过滤器影响。若在自己的模板输出这个片段，需要对最终 HTML 建立明确的信任和过滤约定。

本次验证发现，直接使用文章白名单可能删掉音频需要的 `<source>`。可以在文章白名单基础上补充实际需要的元素：

```php
$allowed_audio = wp_kses_allowed_html( 'post' );
$allowed_audio['source'] = array(
    'src'  => true,
    'type' => true,
);

echo wp_kses( $audio, $allowed_audio );
```

这只是适用于此类音频输出的示例，不是所有媒体组件的通用白名单。要测试播放控件、音源地址、回退链接，以及自己依赖的属性是否保留。安全过滤器可能规范化空白或样式，不必要求过滤前后字符串完全相同。

### 2.7 JavaScript 和 JSON：处理每一层上下文

不要手工拼接不可信值生成 JavaScript 表达式或直接拼 `<script>` 标签。优先使用 WordPress 的脚本注册和数据传递接口。

- `wp_localize_script()` 适用于本地化数据；它会处理传入数据，不要先把整个翻译字符串做 HTML 转义再传入。
- 复杂配置可通过 `wp_add_inline_script()` 配合 `wp_json_encode()` 传递；嵌入脚本上下文时考虑 `JSON_HEX_TAG` 等编码选项，防止内容形成脚本结束标记。
- JSON 放入 HTML 属性时，还需要外层 `esc_attr()`。
- 数据嵌入 JavaScript 字符串，再嵌入 HTML 属性时，要逐层编码；只对最外层属性做转义，不会自动修复内层表达式的引号问题。
- JavaScript 渲染普通文本优先使用 `textContent`，避免把数据直接赋给 `innerHTML`。

API 响应使用匹配的 WordPress 接口，例如 REST 的 `rest_ensure_response()`、AJAX 的 `wp_send_json_success()`，不要把 JSON 当普通页面 HTML 随意 echo。

## 3. RSS 和 XML 专项检查

本节是本次修复中补充发现的问题，不是审核邮件单独列出的新指控。

### 3.1 HTML 转义不等于 XML 转义

`esc_html()` 可能保留 `&copy;`、`&nbsp;` 等 HTML 命名实体。普通 XML 并不内置这些实体，因此下面的输出可能导致整个订阅无法解析：

```php
// 不适合普通 XML 文本节点。
echo '<title>' . esc_html( $title ) . '</title>';
```

改用 XML 上下文处理：

```php
echo '<title>' . esc_xml( $title ) . '</title>';
echo '<enclosure url="' . esc_xml( esc_url_raw( $url ) ) . '" />';
```

同时检查作者、节目标题、分类属性、版权、GUID、人物信息等字段，不要只改第一个 `<title>`。

### 3.2 CDATA 保护的是 XML 边界

CDATA 内容中出现 `]]>` 会结束当前区段。需要把它拆分为相邻的 CDATA 区段，避免内容突破边界：

```php
$text = str_replace( ']]>', ']]]]><![CDATA[>', $text );
```

还应按 XML 版本处理非法控制字符和无效编码。移除非法字符时保留合法的换行、制表符、中文和 emoji，并测试无效 UTF-8 的处理结果。

**CDATA 不是 HTML 安全过滤器。** 它能保证 XML 边界，不会自动清理其中的脚本或事件属性。`the_content` 过滤链也不能被当作 HTML 安全过滤器。

对于需要保留文章 HTML 的 RSS，应明确内容信任边界。不要在不了解影响的情况下套用通用白名单，否则可能删除正常的嵌入内容；若允许不可信来源提交 HTML，则必须在适当边界限制它。

### 3.3 XML 回归测试样例

至少测试：

- `&copy;`、`&nbsp;`、`&amp;`、双引号和尖括号。
- 带多个查询参数的 URL。
- `]]><unexpected/>` 等 CDATA 终止内容。
- 非法 XML 控制字符、中文、emoji。
- 空订阅、正常剧集、可选字段缺失。
- 用 XML 解析器真正加载生成结果，而不只是肉眼查看字符串。

## 4. 全局名称与前缀

### 4.1 选择足够长、独特的前缀

官方最佳实践要求前缀至少四个字母，并建议五个或更多；本次审核明确拒绝了三字母 `ars` 前缀。新插件应优先选完整、独特且能识别插件的名称，不要只追求刚好达到长度下限。

需要检查的范围包括：

- 全局函数、类、接口、trait 和命名空间。
- 常量和 PHP 全局变量。
- Options、transients、数据库表等持久化标识。
- AJAX action、后台保存 action、自定义 hooks、短代码。
- 插件注册的资源 handle、REST 命名空间等共享标识。
- JavaScript 的 `window.*` 全局对象及 `wp_localize_script()` 的对象名。

本次被明确指出的是 `arsFeaturedColumn` 和 `arsFieldsL10n`。**PHP 类有命名空间，不代表注册到 JavaScript 的全局名称也已经被隔离。**

### 4.2 不占用核心保留前缀

不要把 `wp_`、`_`、`__` 等用作自己独立全局函数或其他全局名称的前缀，也不要冒用其他插件或项目的命名空间。

正常调用 WordPress 的 `__()`、`_n()` 等翻译函数没有问题。WordPress 约定的受保护元数据键可以有前导下划线，但其插件名称部分仍应独特，不能把裸下划线当作插件前缀。

### 4.3 `function_exists()` 不是解决冲突的主要方案

```php
if ( ! function_exists( 'generic_save' ) ) {
    function generic_save() {
        // ...
    }
}
```

这种写法可能避免重复声明，却让插件依赖先加载的同名实现，仍会出错。插件自己的全局代码应使用独特前缀或命名空间；共享库的兼容策略需要单独设计。

### 4.4 已发布标识不能盲目全局替换

改名前先盘点：

- 旧内容类型、分类、设置和元数据是否还读得到。
- 历史统计表、缓存和浏览器播放状态是否需要迁移。
- 主题覆盖路径、事件、CSS 选择器、REST 消费者是否依赖旧名称。
- 是否超出 WordPress 的标识符长度限制。

例如 WordPress 文章类型名称最多 20 个字符；`a_ripple_song_podcast` 已有 21 个字符，不能直接拿来注册。

新插件从第一天统一命名最省事。已有插件根据审核要求和兼容性设计改名范围，必要时提供可重复执行且不会覆盖新数据的迁移，不要为了统一外观导致用户数据无法访问。

## 5. 隐私、外部请求与 Google Fonts

### 5.1 加载外部资源也是一次数据传输

即使没有调用统计 SDK，访客浏览器加载 Google Fonts、第三方脚本、图片等资源时，也会向外部服务发送请求元数据。

本次自动预审明确指出：播放器在没有 opt-in 机制的情况下加载 Google Fonts。因此，不能以“它只是字体”或“我没主动上传邮箱”为由忽略问题。

优先方案：

1. 使用设备可用字体，不产生字体下载。
2. 确需特定字体时，在许可允许的前提下本地提供必要资源，评估字符集和包体积。
3. 如确需第三方服务，明确其用途、何时请求、传输什么信息，并按官方规则设计授权流程；不要默认把任何外部资源都视作服务例外。

本地化字体后仍要附带适当的许可和来源信息。本次本地字体让安装包显著增大，因此最终选择了不再附带字体；这属于产品和体积取舍，不是“官方禁止打包字体”。

### 5.2 统计和遥测必须区分用途与去向

审核邮件明确要求：使用跟踪必须可选、默认关闭，并获得明确同意。不能把同意隐藏在文档或条款中，也不能在用户选择前先发出请求。

本次邮件还明确说明，不允许用 Google Analytics 跟踪 wp-admin 使用情况，即使提供 opt-in 也不行。

检查数据时应区分：

- 插件把使用情况发送给作者或第三方的遥测。
- 站点自身为功能需要记录的本地数据。
- 用户配置后使用的外部服务。

不要因为数据仅留在本站，就跳过数据最小化、保留时间和隐私说明；也不要把所有本地统计一概描述为向作者“回传”。是否需要额外授权，应按实际功能、数据和最新指南判断。

### 5.3 用户指定 URL 的功能也要说明

编辑者主动填写的远程音频、封面、章节或字幕地址，与隐藏的遥测用途不同，但仍需要说明：

- 什么操作触发请求。
- 是服务器请求还是访客浏览器请求。
- 请求发送到哪里、为了什么。
- 是否传输用户或站点信息。
- 缓存时间、下载限制和失败行为。
- 固定外部服务的条款、隐私政策等链接。

输入 URL 后的服务端请求还应做安全验证，避免任意协议和不受控目标；使用合适的 WordPress HTTP 接口，并限制超时和响应体积。

### 5.4 排查所有请求入口

检查 PHP、JavaScript、CSS、编译产物和嵌入组件，而不是只搜索 `wp_remote_get()`：

- `wp_remote_*()`、`wp_safe_remote_*()`。
- `fetch()`、XHR、`sendBeacon()`、分析 SDK。
- 远程 `wp_enqueue_script()`、`wp_enqueue_style()`。
- CSS `@import`、`@font-face`、`url(...)`。
- `iframe`、远程图片、预连接和动态创建的脚本节点。

保留一个请求清单：**发起方、目标、触发条件、用途、数据、默认开关、授权依据、文档位置**。

排查浏览器网络时要定位请求来源。主题、其他插件和被测试插件可能同时加载资源，不能仅凭域名出现就把请求归给某个插件。默认主题和干净环境有助于隔离来源。

## 6. README、许可证和实际发布包

本节包含审核邮件的提交要求，以及本次工具检查得到的发布注意点。

### 6.1 文档必须对应真实行为

- 外部服务发生变化时同步修改说明；移除外部字体后，不要继续声称浏览器会连接 Google。
- 说明数据保存位置、用途、保留时间和发送对象；本地数据也要按实际情况描述。
- 压缩、编译的 JS/CSS 应提供可访问的源码或开发仓库，以及必要的构建说明。
- 打包的代码、字体、图标等第三方资源必须具有允许分发且与目录要求兼容的许可证，并保留相应声明。
- 每次正式发版递增版本号，保持插件头、运行时版本常量、包元数据和 README Stable tag 一致。

区分两个版本说明区块：

| 区块 | 用途 | 适合写什么 |
| --- | --- | --- |
| Changelog | 记录每个版本发生了什么 | 新功能、修复、行为变更 |
| Upgrade Notice | 提醒用户升级前需要知道什么 | 兼容变化、迁移、需要采取的操作、重要修复 |

Upgrade Notice 保持简短；没有额外操作要求时，不必复制整份 Changelog。

### 6.2 检查最终 ZIP，而不只检查仓库

建立明确的发布文件清单，只打包运行所需文件。通常不应包含：

- `.git`、`.github` 和本地工具配置。
- `node_modules`、开发脚本、缓存、日志和测试数据。
- `AGENTS.md`、内部开发文档及无关文件。

源码可以随包提供；内部开发资料和整个依赖开发目录不等同于必要源码。若选择不把构建配置放进包内，应提供清楚的源码位置和构建方式。

发布检查包括：

- 解压后的目录结构、插件主文件、依赖和构建产物完整。
- 没有丢失必要资源，也没有混入已删除资源。
- PHP 版本要求和运行环境一致。
- 压缩包可以解压，并能在干净站点安装、激活。
- 对**实际准备上传的文件集**再运行检查。

源码目录上的开发文件提示，不代表生产包一定有同样问题；生产包通过检查，也不能替代对源码安全边界的人工审查。

## 7. 工具检查、测试和误报处理

### 7.1 Plugin Check

本次使用过的命令如下；运行前需安装并启用 Plugin Check，具体选项以所用版本帮助为准：

```bash
wp plugin check your-plugin-slug --include-experimental --format=table
wp plugin check your-plugin-slug --checks=late_escaping --include-experimental --format=table
```

在支持目录参数的版本中，可以检查只包含发布文件的暂存目录：

```bash
wp plugin check /absolute/path/to/staging/your-plugin-slug --include-experimental --format=table
```

不要把 `--ignore-errors`、`--ignore-warnings` 或批量 `phpcs:ignore` 当作“通过审核”。过滤参数适合定位问题，不会修复代码。

Plugin Check 和 PHPCS/WPCS 可以帮助发现问题，但不能证明：

- 所有输出都安全。
- 所有外部请求都已获得合适授权。
- XML、音频和图标在过滤后依然正常。
- 已满足全部目录指南或一定能通过人工审核。

### 7.2 干净安装和调试测试

审核邮件明确要求：在干净 WordPress 安装上启用 `WP_DEBUG` 测试，不能只运行静态扫描。

建议验证：

- 安装、激活、停用，没有致命错误。
- 默认设置、保存设置和重新加载。
- 空数据、正常数据及特殊字符输入。
- 前台、后台、AJAX、REST、RSS 等实际涉及的入口。
- 主要功能回归：例如播放、媒体选择、列表操作。
- PHP 调试日志、浏览器控制台及网络请求。
- 已有用户升级后的数据和配置是否保留。

安全过滤回归要兼顾两面：恶意标记确实被处理，正常功能所需标记也没有被删掉。

### 7.3 Warning 和人工判断

本次的 `load_plugin_textdomain()` 提示是建议项：WordPress.org 可以自动加载目录提供的翻译，但插件若还支持包内翻译或其他安装渠道，需要先核对加载路径和时机，不能为了清掉 warning 直接删掉。

对每条提示判断：

1. 是实际缺陷、兼容风险、目录要求，还是工具无法理解的上下文？
2. 发布包是否真的包含被指出的文件或代码？
3. 能否用最小修改解决，并验证行为？
4. 若认为是误报，能否提供明确调用链、代码示例和复现结果？

“工具没有报错”和“人工确认不适用”是不同结论，应分别记录。

## 8. 发布前可复用清单

### 输出与标识

- [ ] 已检查 `echo`、`print`、`printf`、模板、回调和返回 HTML 的输出链。
- [ ] 纯文本、属性、URL、textarea、HTML、SVG、XML 分别使用适当处理。
- [ ] 数据库存储值、翻译、nonce 和生成字符串也纳入检查。
- [ ] 没有用早期转义、函数名或忽略注释代替最终输出安全边界。
- [ ] HTML/媒体白名单保留必要功能；RSS 已经 XML 解析器验证。
- [ ] PHP 与 JavaScript 全局标识独特，长度符合要求。
- [ ] 已发布标识改名时有兼容与迁移验证。

### 隐私与资源

- [ ] 已盘点服务器和浏览器两侧的外部请求。
- [ ] 非必要外部资源已移除或本地化，没有隐藏的字体、脚本或遥测请求。
- [ ] 可选跟踪默认关闭，明确授权发生在首次请求之前。
- [ ] 未使用 Google Analytics 跟踪 wp-admin。
- [ ] 服务、数据用途、保留时间及外部请求在文档中准确说明。
- [ ] 第三方资源许可、来源和分发条件已核对。

### 构建、测试与版本

- [ ] 所有运行时版本声明、Stable tag 与目标版本一致。
- [ ] Changelog 已更新，需要提醒用户的升级影响已说明。
- [ ] 已完成构建；压缩资源有源码及构建说明。
- [ ] 最终 ZIP 文件集完整，不含内部开发资料和无关文件。
- [ ] 对最终文件集运行 Plugin Check；错误和警告均已逐项判断。
- [ ] 干净站点开启 `WP_DEBUG`，安装激活和核心功能测试通过。
- [ ] 测试日志和验证范围有记录，没有把未测试内容写成已通过。

### 审核沟通

- [ ] 已处理邮件中的全部问题，并搜索同类遗漏。
- [ ] 已在“Add your plugin”页面上传修正版。
- [ ] 回复原审核邮件线程，而不是新建邮件。
- [ ] 回复简短、直接，只提供重要上下文或澄清，不粘贴冗长修改日志。
- [ ] 如需修改插件 slug，明确提出目标 slug；只改显示名不够，获批后不能随意改 permalink。

审核邮件提醒不要频繁催问进度，也不要只修少量问题就反复提交。遇到不能确认的要求，先解决其余问题，再带着具体示例向审核团队澄清。
